# Response Usage Attribution Design

応答ごとのトークン数を、成功したTask操作と構造的に結び付け、一意な作業単位へ帰属させる機能の設計書である。同一turnの連続Taskを区分し、中断・遅延・対応不能の際も観測した数値と限界を保持する。

<a id="applicability"></a>

## 適用条件と責任

本書は[authority index](authority.md#conditional-response-usage-attribution-design)が案内する条件付き設計の所有者である。合意済みの応答境界・集計規則と実装の責任分担を定める。文書の登録だけでは稼働中の方式、schema、公開JSON、host設定を切り替えない。

対応する機能部分の実装・隔離検証・独立レビューと、下表の現行所有者・直接結合する契約の同期が成立してから、その部分を製品に適用する。開始・完了と実行別集計が成立した後に停止・再開へ進む既存の順序を維持する。一部の対応成立をもって、未実装の停止区間や未検証のhost形式まで対応済みとはしない。着手可否・完了証跡は公開CLIのlive Taskを正本とする。

本書は現在のDB・Task操作・Setupの所有権を移転しない。新しい実行計画、Taskの分割や受入条件の追加、通常操作の権限拡大を行わない。物理schema、具体的なJSONフィールドとエラーコード、host adapterの採用文法は実装する範囲の現行所有者へ記載する。本書は機能としての境界と責務を保ち、それらの一覧を二重管理しない。

完了Evidenceのトークン収録・封印時点・版管理、Task資料フォルダ、数値未取得の別原因の修正は対象外である。数値DBをcoreの品質・完了ゲートに組み込まず、計測失敗で業務完了を取り消さない。

<a id="boundary-rules"></a>

## 応答境界と作業単位

計測単位は数値を持つ `(provider, response_id)` であり、画面上の発言やツール結果ごとの文字数ではない。その入力・出力を一つの単位として扱い、本文の意味、コマンド時刻、経過時間から推定分割・按分しない。

### 開始と完了

| 状況 | 採用する境界 |
|---|---|
| 開始と同じturnに採用可能な一連の事前確認がある | その最初の確認コマンドを含む応答から、選んで開始したTaskへ帰属 |
| 確認と開始が同じ応答、または同じturnに採用可能な確認がない | 開始コマンドを含む応答から |
| A確認、B確認からAまたはBを開始 | 最初のA確認から。確認候補と開始先の一致は要求しない |
| 他Taskを実行中に次Taskを確認 | 実行中Taskを優先し、その確認を次Taskの起点に使わない |
| 開始に至らない確認 | 他の有効な帰属根拠がなければ帰属なし。ただし直前Taskの完了turn内はその完了turn規則で扱う |
| 手動完了 | Taskを手動完了したturnが完了turn |
| 自動完了 | 実際の自動完了通知turnが完了turn。送信acceptedだけで受領を捏造しない |
| 完了turn内に次Task起点がある | 次Taskの起点応答の直前までを前Taskへ帰属 |
| 完了turn内に次Task起点がない | 同じturnの残りの応答を前Taskへ帰属 |

成功を確認できた状態変更だけを境界にする。失敗した開始・完了は区間を切り替えず、結果未確認は成功にも失敗にも決めつけない。結果が遅れても、検証できた元の操作応答へ対応付ける。事前確認を採る範囲は元の開始操作と同じturnに限り、前turnや結果受領turnから借用しない。

完了後の別turnの確認を前Taskへ遡って帰属させない。単一の次Task起点と前Taskの完了報告・完了操作が同じ応答なら、その応答全体を次Taskへ帰属させる。下記の複数開始に限る共有例外を除き、前Taskへ二重計上しない。

### 停止と再開

停止は成功したpause/block操作を含む応答まで元Taskへ含め、次の応答から停止扱いとする。これは計測の境界であって、core状態が更新される時刻を遅らせる規則ではない。

再開は開始と同じ起点規則を使う。再開と同じturnに採用できる事前確認があればその最初から、なければ再開コマンド応答から計上する。停止と単一の次Task開始・再開起点が同じ応答なら次Taskを優先する。

別応答で「B確認 → A停止 → B開始」と並ぶ場合、停止応答までA、B開始応答からBとする。A実行中の確認をBへ付け替えない。停止後に新たな有効な確認があれば、その系列の最初を同じturn内の起点にできる。

停止後、次の有効な開始・再開起点までの応答は、他の有効な帰属根拠もなければ帰属なしである。後のTaskに空白区間を一括帰属させず、別turnへ遡らない。失敗した停止・再開は区間を切り替えない。チャット中断の扱いは[中断と部分観測](#partial-observation)による。

### 実行と完了回

同一turnでも「A開始・完了 → B開始・完了 → A再開始・完了」のA初回、B初回、A再開回を既存executionと完了回で区別する。開始応答を確認できる各区間の数値を別々に取得できるようにし、同一Task IDだけで一つの専有値へ潰さない。

pause/blockからの再開は同じexecutionの複数区間として扱い、done後のreopenと区別する。ready/cancelledへの移行など、現行coreがexecutionを終了する操作の同一性も変更しない。Task累計や完了回との対応は既存のcore関係から作り、帰属のための新しい状態操作を発生させない。

<a id="shared-responses"></a>

### 共有する応答の範囲

同じ数値応答に複数の作業単位の成功した開始・再開が含まれるとき、分割できないその応答だけを共有分とする。例として、同一応答内の「A開始・完了 → B開始」はA/Bの作業単位に共有する。前後の専有応答まで共有へ広げない。

各作業単位の専有分・共有分と共有先Task/executionを区別する。Task全体や複数Task合計は元応答キーの和集合から計算し、共有分を重複加算しない。A/B共有とB/C共有を理由に各Taskの全応答を一つの共有集合へ拡張しない。後続応答は確認できた状態順序による通常規則へ戻す。順序を確認できない場合は、その影響範囲を不明にする。

<a id="responsibility-map"></a>

## 処理とデータの責任分担

| 処理 | 入力と出力 | 責任の境界 |
|---|---|---|
| source admissionと数値取得 | 登録済みsourceから元応答の数値・同一性 | 現行adapter/repositoryの検査と重複排除を再利用 |
| 観測抽出 | host構造からcall・handle・ack・確認観測 | 本文を捨て、閉じた構造のみを数値側へ渡す |
| 成功照合 | ackとadmitted coreからtransition/execution | SQLはrepositoryへ集約。現在のownerへの近接推定をしない |
| 元応答解決 | call/resultと非同期連鎖から操作応答 | host形式ごとの一意性と資格条件を検証 |
| 境界計算 | 成功操作・確認系列・明示順序から応答区間 | pureな計算として検証し、core状態を書き換えない |
| 帰属と集計 | 元応答キーからexecution集合・専有/共有数値 | 元キーの和集合。異なるprovider/modelを無条件に合算しない |
| 保存と公開 | 新しい観測・帰属basisから投影と後継snapshot | 数値transactionと不変記録、最後の正常出力を保持 |

source読取・host操作・ファイル公開を数値writerの中に混在させない。既存の収集契機と登録範囲を使い、通常のLLMに追加確認コマンド・poll・stopを要求しない。物理モジュールの新設・配置は、既存のadapter、帰属計算、repository、publicationの責任に沿って実装側で決める。

<a id="partial-observation"></a>

## 中断と部分観測

チャットの`turn_aborted`はhost側の中断記録であり、Taskのpause/block操作でも、成功済み操作の取消でもない。`reason=interrupted`から、入力ミスなどユーザーの具体的な理由を推測しない。

| 数値・操作・帰属の観測 | 計測上の扱い |
|---|---|
| 中断前に応答数値と有効な帰属を観測 | その数値と帰属を保持 |
| 数値はあるが操作・応答の対応が不足 | 数値を保持し、帰属不明を表示 |
| 操作成功は確認したが該当応答の数値がない | 操作成功は保持し、数値未取得。前後の数値の借用やゼロ補完をしない |
| コマンド発行のみ観測し、成功・失敗が未確認 | 操作結果未確認。成功した境界を作らず、影響範囲の帰属不明を残す |
| 明示的な失敗結果 | 区間を切り替えない。失敗応答の実測数値は有効な既存帰属規則で扱う |
| 数値が後で観測された | 元応答キーで重複排除して追補。中断を理由に捨てない |

成功結果の欠落を「操作失敗」として前Taskへの確定帰属に置き換えない。未確認操作が境界を変え得る範囲は不明として扱い、既に独立した根拠のある前後の応答まで一律に捨てない。帰属なしは規則上の割当先がないことを確認できる場合だけであり、帰属不明・数値未取得・実測ゼロと別である。中断や静かなファイルは収集完了の証明にもならない。

未確認callの不明範囲は、次の任意の状態eventでは解除しない。有効な開始・再開、または影響する実行状態を再確定できる対応済み操作を回復境界とする。無関係なblocked/paused Taskをready/cancelledへ整理しても、古い実行の専有配賦や確定した帰属なしには戻さない。後から元callの結果と応答対応を検証できれば、その元操作に基づいて再評価する。

<a id="observations"></a>

## 観測関係と処理の分離

以下は必要な論理関係であり、物理DDLや公開JSONのフィールド名は直接結合する現行所有者で確定する。保存項目は閉じた型・長さ・固定理由を定め、本文を持たせない。

| 関係 | 保持する最小の情報 |
|---|---|
| 呼出しと結果 | source incarnation、thread、turn、tool種別、call/item ID、観測順序、対応状態 |
| 呼出しと数値応答 | 元呼出しID、`(provider, response_id)`、対応方法の版、確定根拠または固定の不明理由 |
| 非同期実行 | host tool種別・thread・識別できる実行寿命内のhandle、元呼出し、後続wait/pollの呼出しと結果、終端・競合の状態 |
| 成功したTask操作 | 既存のproject/Task/event/owner generation/status/actorと、照合できたtransition/execution、元呼出しへの関係 |
| 読取確認 | 成功した既知の確認コマンド種別、project、元呼出し・turn・応答順序。確認先Taskは開始先の一致条件にしない |
| 応答の帰属 | 元応答キー、専有または共有のexecution集合、規則の版、帰属なし・不明の理由。数値本体を複製しない |

処理は、既存のsource admission、輸送容器の解釈、ackの検証、元呼出しの解決、数値応答との対応、境界・帰属の計算、集計・投影に分ける。ackを読めること、coreの成功を確認できること、元応答を特定できることは別の判定である。

<a id="operation-response-correlation"></a>

## 元の操作応答へ辿る方法

### 通常呼出し

呼出しの起点を、確認済み新規実行、確認済みpoll、判別不能に分ける。新規実行も既存の閉じた入力形式で積極的に認定し、既知pollに一致しないことを新規実行の根拠にしない。明示的な応答IDがあっても未対応の呼出しの起点は確定しない。判別不能でも検証できた操作成功と数値を保持し、帰属なし・ゼロ・操作失敗に置き換えない。対応形式の詳細は[現行応答境界契約](database-specification.md#response-boundary-attribution)を正本とする。

同じthreadの明示的な`call_id`で呼出しと結果を結ぶ。継承された別thread履歴を除き、IDの重複矛盾、turn欠落、source置換・欠落を検出する。数値応答との直接対応が利用できる形式では、それを検証して使う。

直接対応がない既存Run形式では、同一turnの呼出しから最初の対応結果までに一意な数値応答がある、という観測済み構造を候補とする。ただし、単なる最近傍選択にはしない。採用するformat/version・記録順序の意味、遅延数値、複数呼出し、途中欠落への識別条件をfixtureと該当hostの根拠で確認してから、閉じた対応規則として実装する。条件が成立しない形式は帰属不明に留める。連続した行番号や安定したファイルだけで完全性を証明しない。

### 非同期実行とpoll

例として、R1で開始コマンドを発行して実行Pが返り、R2でPをpollして継続中、R3でPの成功を受け取った場合、R3からPの元呼出しへ戻ってR1に結ぶ。R3は成功を確認した時点、R1は計測上の操作応答である。採用可能な事前確認は元の開始操作と同じturnからだけ選ぶ。

`call_id`に加え、`exec_command`の`session_id`や外側`exec`の`cell_id`など、実際に対象形式が返すhandleとwait入力の対応を閉じたadapterで解釈する。異なるtoolの数値が偶然等しいだけでは結ばない。handleの所有範囲・寿命・再利用を識別できない、複数起点が競合する、途中結果がない場合は不明にする。成功ackがあるpollを新しいTask開始として数えない。

pollが別turnに跨っても、検証できた呼出し連鎖は元の操作へ戻す。事前確認を結果受領turnから選び直さない。手動完了turn・実際の自動完了通知turnは既定の境界規則と構造的根拠で識別し、単に成功JSONを読んだturnへ移さない。

### 複数コマンドと内側実行

一つの外側`exec`に複数の内部呼出しがある場合、外側の数値応答を特定できても、各成功結果の元コマンド・Taskとの関係は別に検証する。構造で対応が分かる固定容器や実行handleを使い、任意JavaScript/PowerShellを実行・評価したり、本文の意味から結果の順番を補ったりしない。

内部handleを文字列のliteralとして確認できる等の対応範囲を明記する。変数参照、複数結果の無標識連結、ID再利用、完了順序不明を汎用正規表現で解決した扱いにしない。同一数値応答の共有先を確認できても、その後の状態順序を確認できなければ後続範囲は不明にする。全経路の推測対応を実装開始条件にせず、対応する経路と不明に落とす経路を検証可能に定める。

<a id="transport-and-success"></a>

## 成功応答の読取

1. **既知の輸送容器をほどく。** 現行のtext/input_text、execのoutput/content、既知のexecヘッダを基礎とする。未知の辞書全走査や本文中の任意JSON探索はしない。深さ・サイズ上限は現行の有限処理を維持し、超過を黙って成功扱いしない。
2. **対象形式のJSONを読む。** E2のPython起動警告は、観測済みの警告形式が既知容器の先頭にある場合だけを候補とし、許容文法と否定例を定める。個人の絶対パスを条件へ埋め込まず、本文・パスは保存しない。任意の行を「警告らしい」と捨てて最初の`{`を探す処理は採用しない。複数JSON、後続テキスト、部分JSONは明示した輸送文法で扱い、未知の付加部分を都合よく読み飛ばさない。
3. **Taskgovの成功を検証する。** `ok=true`、既知command、状態変更の有無、project/Task/event/owner generation/status/actorを検証し、既存repository経由で確定済みcore transitionへ照合する。shell終了コード0、文章の「成功」、現在のTask状態だけでは成功境界を作らない。
4. **登録時の参照を維持する。** 単一・一括登録の閉じた同一ack内参照を、その元応答の文脈で解決する。任意JSON Pointerや別応答からの穴埋めを導入しない。参照先不一致は不明にする。
5. **必要な構造だけを残す。** 数値とID・種別・順序・固定診断のみを保存する。警告本文、コマンド本文・引数、prompt、会話、思考、生provider本文、本文digestを数値DBや診断ログへ追加保存しない。

呼出し引数のうちhostのwait handleなどの閉じた構造を一時的に読むことと、Taskの意味をshell本文から推測することを区別する。Task操作の意味と成功はack/coreで確かめる。既知形式の一部が読めない場合、既に独立検証できた操作と曖昧な部分を区別し、後者を黙って欠落させて完全な区間にしない。

実行寿命の終了は成功応答の解釈と分ける。同じcall・検証済みbatch位置・既知pollに対応する完全なprocess結果容器の整数終了コード、または既知のprocess終了ヘッダを根拠にする。通常文字列・空・JSON・途中JSONのstdoutは、正しく終了した実行の保留枠を占有し続けない。一方、終了コードからTask操作の成功・元応答を作らない。未知または破損した容器、handle競合、切断表示、対応が不明な複数結果、外側の`Script completed`だけでは内側の保留を解除しない。具体的な閉じた形と上限は[現行応答境界契約](database-specification.md#response-boundary-attribution)に従う。

不完全・矛盾したprocess容器の本文に有効なTaskgov応答があっても、操作の観測だけを保持し、それで実行寿命の不明を解除しない。終了コードが欠落またはnullの場合も、processメタデータを共通の検査で認識して本文から実行handleを作らず、正当な継続中容器のトップレベルhandleだけを使う。応答と輸送容器が同じオブジェクトに混在する場合も、output/contentの子要素が未解決なら保留を解除しない。

batchの位置を取り出す前にもprocess容器の境界を維持し、そのstdoutに書かれたindexを外側の結果位置として採用しない。通常実行でも重複JSONキーを持つ容器からhandleを取得せず、別の独立した結果容器と区別する。

成功本文を読む際も、対応が証明されていないindexを消さず、通常実行・poll・既知slot内の追加indexから帰属起点やhandleを作らない。text/input_textの余分な項目を未知の容器として各経路で同じように扱う。元JSONLのobject値でも重複キーを後勝ちで確定せず、そのobjectだけを不透明な値にする。独立した正常な兄弟要素・数値は維持し、この一時的な曖昧さや元本文を保存しない。

外側のrecord/payload識別構造が欠落・不透明化した場合は、無関係なrecordとして読み飛ばさず、保留中の対応を不明化して候補区間を閉じる。本文だけが不正な場合は確認できたcallの最初の結果として区切りを保持する。JSON文字列・object値・poll入力で同じ曖昧さの規則を使い、不正な応答1件で独立した正常な兄弟や既確定の過去・後続callを捨てない。元の数値を維持し、版更新後も登録済み原本の再確認が済むまで回復済みとしない。

意味上の観測結果と未確認部分の有無は別々に返す。project/Task/eventの識別欠落・不一致を、正常に識別できた対象外応答と混同しない。Task・レビューの一括登録応答の項目も独立して検証し、正常項目を保持したまま不正項目の未確認を終了判定へ伝える。正常な兄弟の成功で未確認を消さず、別に確認できたprocess終了の根拠とは区別する。通常応答の独立した不正本文は、正常な兄弟の確立済み起点まで無効化しない。batch全体の重複拒否を通常応答のindex検出へ流用せず、実行寿命・handleの判定にもobjectと文字列で同じ規則を適用する。

旧turn単位の読込も同じ完全容器の検証を通し、文字列とobjectで採否を変えない。callのturn・tool名構造を失った場合は早期return前に対応を不明化する。レビュー読取・保存・待機終了も必要な識別情報を検証し、表示ラベルだけで実行の終了と判定しない。

<a id="attribution-projection"></a>

## 事前確認と帰属計算

確認コマンドは新しい読取観測として扱い、状態変更eventを捏造しない。成功した公開CLIの確認ack、project、元応答・順序を用い、開始操作まで同一turn内の採用可能な確認系列を保持する。`task.context`等の具体的な対象コマンドと成功shapeは実装前に公開契約から列挙する。何でも読取なら確認とする拡張はしない。

確認候補と開始先のTask一致は要求しない。他Taskの実行中はそのTaskへの帰属を優先し、成功した開始に使えなかった確認、停止後の新たな確認、完了turn内に残った確認を[応答境界](#boundary-rules)で区別する。系列の選択にLLMの意図や文章の意味を使わない。

応答入力・出力は一つの数値単位である。次Task優先と同一応答の複数開始だけの共有例外を適用し、元応答キーからexecution集合への関係で専有分と共有分を集計する。共有関係を推移的に拡張して、A/B共有を理由にAの別の専有応答まで共有にしない。Task全体・複数Task合計は元応答キーの和集合から計算する。

初回と完了後の再開始は既存の別execution/完了回へ結び、pause/blockからの再開は元のexecutionへ戻す。core状態やevent時刻を計測の都合で変更しない。数値応答との対応だけでなく、元execution・完了回を照合できない場合も推定専有値を作らない。

レビュー担当・実受領通知等の独立した有効関係は別入力として維持する。停止で一律に消さず、親の状態起点や共有例外だけで誤って上書きしない。新しい応答境界との重なりを検証し、元応答キーで一度だけ合算する。通知文や親子関係だけで新しい参加者・turnを追加しない。

<a id="persistence-and-replay"></a>

## 保存と再収集

数値schema側に必要な関係を置き、Taskのトークンカラムを配列化しない。具体的なtable・JSON名、schema番号、algorithm版は実装時に正式所有者へ記載する。coreのexecutionと完了回が満たしている同一性を再利用し、数値帰属のためだけに新しいTask状態遷移を作らない。

呼出し・待機連鎖・確認系列は収集sliceやプロセス再起動を跨ぐため、閉じた再開用メタデータとして持つ。cursor、source incarnation、sanitized prefixの版、数値観測、関連観測、dirty範囲を同じ数値transactionで確定する。前後のsliceに分かれた結果・使用量を処理できるようにし、途中で打ち切った連鎖を成功や帰属なしにしない。保存量の境界を決め、上限で失われた対応は明示的な不明とする。

遅延した成功・数値・関連は影響する旧新の範囲を再評価する。全読取と増分読取で、同じ入力とcore basisなら元応答集合・帰属・数値・診断が一致することを受入条件にする。呼出し観測の再読込や結果の重複から、新しい開始・共有分・数値を増やさない。矛盾は後勝ちにしない。

source置換・切詰め・core復元では既存のadmission、prefix監査、再照合を維持し、不足した関連を最新のownerや別完了回へ付け替えない。旧形式しか残っていない履歴は保持して境界不明を示し、推定で細分化しない。新投影が必要な場合も既存の不変snapshotと完了Evidenceは上書きせず、互換性と後継関係を定める。原本の再読込は既存の登録済みsource範囲に限る。

旧読取が通常stdoutの終了を認めず保持した保留と、その容量超過後に失われた起点は、parser版のprefix監査と元sourceの再読込でのみ回復する。逆に、旧読取が曖昧な終端から保留を解除した判定も、新しいparser版で原本から再構成する。新adapterのロード時に状態を一括削除せず、原本を再確認できない場合は不明を維持する。schema・現用設定の変更はこのparser更新に含めない。

製品の保存形式変更には明示Setupでのmigrationと旧版保持の検証が必要。本書の適用は実環境のSetupやmigrationを許可しない。計測・公開失敗でTask完了を止めたり、成功したTask操作の再実行を要求したりしない。

## 受入検証

原ログ・私的本文をテストへコピーせず、観測した形を再現する最小の合成fixtureを作る。既存の開始・完了・再開始・停止規則の全受入条件に加え、次を検証する。

| 分類 | 主なケースと期待結果 |
|---|---|
| 中断 | 数値あり/なし、成功前/成功後中断、後から数値到着。成功・欠測・不明・ゼロを区別し数値保持 |
| 通常対応 | 明示関係、観測済み単一候補、対応なし、複数候補、欠落・順序不整合・継承履歴。資格を満たさない対応は不明 |
| 非同期 | 元execから複数poll、外側cellのwait、別turnの結果、handle再利用・別thread・混在・欠落。結果応答を元操作へ代用しない |
| 内側複数操作 | 順序確定/不明、結果到着の逆順、同一応答の複数成功、一部失敗・結果なし。共有対象と不明範囲を限定 |
| 読取 | 既知容器、既知の先頭警告、未知警告、文中の偽ack、複数JSON、後続テキスト、途中JSON、サイズ・深さ上限。任意JSON探索をしない |
| 成功照合 | `ok=false`、終了コードだけ、metadata edit、Task/event/project不一致、core行消失、単一/一括登録の閉じた参照、参照改竄。未確認を失敗で代用しない |
| 確認起点 | 最初の候補不一致確認、同一応答確認、別turn確認、実行中Task優先、未開始確認、遅延結果。開始・再開元turnだけから採用 |
| 作業単位 | A1/B1/A2、同一応答だけの共有、前後の専有、元キー合計、pause/blockの同一execution。旧共有グループを専有値にしない |
| 増分 | 全読取との一致、slice境界、再起動、重複、同時収集CAS、遅延、source置換、core復元、移行中断。raw本文を残さず安全に再収集 |
| 既存経路 | review/wakeの元execution・実受領turn、完了後の遅延数値、不変snapshot・Bundle、読取無変更、計測失敗でも品質ゲート維持 |

対応する既存テストは`test_usage_turn_adapter.py`、`test_usage_attribution*.py`、`test_usage_incremental*.py`、`test_usage_evidence*.py`、`test_usage_review_attribution.py`、`test_usage_wait*.py`、`test_usage_setup.py`と結合先。実装変更に応じて最小の意味ある範囲を選び、文書契約・配布物整合・Tier 2独立レビュー2件を満たす。

<a id="implementation-qualification"></a>

## 実装で確定する技術条件

[応答境界](#boundary-rules)は合意済みである。実装担当が機能内の作業として確定するのは、対応するRun形式と順序の採用条件、非同期・内側実行の閉じた読取範囲、確認コマンドのallowlist、警告等の輸送文法、保存項目・固定診断・移行形式である。観測根拠と隔離fixtureでこれらを確定し、対応外は不明へ落とす。標本に現れなかった形式の推定対応や新しいhost機能の導入を必須とはしない。

開始・完了分類と作業単位別集計が検証・レビューを通過してから、停止・再開分類へ進む。技術条件を機能内で検証することと、追加の製品判断や外部対応を待つことを区別する。着手可否・順序はlive Taskを参照し、本書へ状態を複製しない。

適用が成立した部分については現行所有者との一致を維持する。本書全体が採用済みになるときは、条件付きである理由と移行説明を見直し、必要なauthorityの変更を同じレビューで扱う。設計書そのものを自動廃止したり、履歴だけに現在の規則を残したりしない。

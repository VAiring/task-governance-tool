# 比較計測の共通実行手順：待機中継

この文書は実験実施者用です。今後のRun準備で、既存の共通依頼に付ける
**両群同一の待機案内**をここで管理します。製品Skillの規則ではありません。
既存の実験README・凍結Run・開発アプリを書き換えず、今回の作業では導入や
新しい実開発計測を開始しません。適用時はそのRunの開始承認が別途必要です。

## 採用する範囲

既に承認され、起動済みの独立した非対話処理が複数ある場合、その出力取得を
`functions.exec`の**1回の並列poll**にまとめます。完了したIDを次の待機から外し、
各返却チャンクは1回だけ受け取ります。新しいプロセスの起動・再実行・書込み・
承認判断・結果の意味判定はまとめません。処理が1つだけなら従来の直接pollで十分です。
何度もpollする隠れたループや、sleepの延長による長時間無応答にはしません。

これは複数のpollを1つのモデル応答にまとめられる限定方式です。単一プロセスの
待機をすべてモデルから隠す機能ではなく、実poll数の減少自体も保証しません。
既に同じ応答でまとめていた箇所には追加効果がありません。

## 公開機能と版の確認

2026-09-13 JST確認。この作業セッションには`functions.exec`と、その中から
呼べる`tools.write_stdin`が実際に公開されています。前者はJavaScriptと
`Promise.all`を利用でき、後者は既存`session_id`への空入力によるpollと、
`exit_code`・実行中の`session_id`・新しい`output`を返す契約です。
実行用セッションIDと`functions.exec`自身の`cell_id`は別物です。
後者が実行中を返した場合にだけ`functions.wait`を使い、元のpollを二重発行しません。

Run11の公開session metadataではDesktop originator、`cli_version=0.153.4`。
これは記録時のCLI版であり、現在のDesktop配布版や機能フラグの証明ではありません。
現在プロセスの公開version情報は取得できなかったため不明とします。
次回は両群に実際に公開されたツール契約を確認し、同じ経路がない場合には
両群とも従来の直接pollを維持します。片群だけ代替SDKや内部APIを入れません。

[公式API説明](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)
にはJavaScriptによるループ・並列呼出が記載されていますが、Responses APIでは
呼出側による有効化・ツール指定が必要です。その説明はDesktopの採用証明では
ありません。本手順は上記の実際の公開ツールだけを根拠にします。

## 両群に渡す共通案内

> 既に起動済みで互いに独立した、入力・承認待ちではない処理が複数あるときは、
> 出力取得だけを1回の並列pollにまとめてよい。返されたsession IDだけを使い、
> 同じIDへ同時に二重pollしない。各pollは通常の短い待機窓を使う（この例は10秒）。
> 完了・失敗・判断が必要な出力を確認してから次へ進み、完了済みIDは再取得しない。
> 途中出力も捨てず、必要な進捗通知を維持する。停止要求があれば次のpollを
> 発行せず、既存の停止操作と実行状態確認へ戻る。単一処理や対話・承認待ちは
> 従来経路を使う。待機窓が終わっても実行中なら、処理タイムアウトや失敗とは扱わない。

両群へ同一バイト列・同じ時点で配布し、モデル・推論設定・検証内容・承認設定を
このために変更しません。配布元文書全体や比較結果を開発担当へ渡す必要はありません。
実施者が開発rootを外から監視する費用と、開発担当のプロセス待機は別集計です。

## 公開ツール用の1回集約例

以下の関数を`functions.exec`のJavaScriptとして使い、続けて
`text(await collectOnce([実際に返されたID, 別の実際のID], tools));`を実行します。
ローカルNodeからDesktopのツールを呼べるという意味ではありません。
対象コマンドは通常の出力枠で必要な結果を取得できる既知の処理に限定します。
出力予算を節約目的で下げず、集約した出力が枠に収まらない場合は従来の個別取得へ
戻します。切詰め・不明な応答から成功を推定しません。

```javascript
async function collectOnce(sessionIds, tools) {
  const observations = await Promise.all([...new Set(sessionIds)].map(async id => {
    try {
      const result = await tools.write_stdin({
        session_id: id, chars: "", yield_time_ms: 10000,
      });
      const status = Number.isInteger(result.exit_code) ? "finished"
        : Number.isInteger(result.session_id) ? "running" : "unknown";
      return { session_id: id, status, result };
    } catch {
      return { session_id: id, status: "unknown", poll_error: true };
    }
  }));
  return {
    observations,
    pending_session_ids: observations.filter(x => x.status === "running")
      .map(x => x.result.session_id),
  };
}
```

返された`pending_session_ids`は次回候補であって自動再実行指示ではありません。
`finished`でも非ゼロ終了は失敗です。出力の意味と既存の検証条件は担当LLMが確認します。
`unknown`は終了不明として調査へ戻し、同じ処理を勝手に起動し直しません。
完了結果はこの呼出内で重複取得しませんが、外側の応答喪失時のexactly-once配送は
保証できません。既存の実行状態を確認し、失われた出力を捏造・再登録しません。

## 通知・停止・時間切れ

| 観測 | 次の扱い |
|---|---|
| `exit_code=0` | 出力と既存検証条件を確認。終了IDを除外する。 |
| 非ゼロ`exit_code` | 失敗を通知し、診断する。残る独立処理まで失敗とはしない。 |
| `session_id`継続、途中出力あり | 出力を保持し、必要な進捗・判断を通知する。 |
| `session_id`継続、出力なし | まだ実行中。待機窓の終了であり、処理の時間制限超過ではない。 |
| poll例外・不明形・外側応答喪失 | 状態不明。完了や停止成功を宣言せず、既存状態を確認する。 |
| 停止要求 | 新たなpollや起動を止め、元のセッションに対する既存停止経路を使う。 |
| 実行元が処理タイムアウトを明示 | 元の失敗情報と終了状態を確認。必要な停止・cleanupを既存手順で行う。 |

10秒はpollの要求窓であり、ホスト遅延も含む厳密な応答時間SLAではありません。
既存の進捗通知間隔（本作業環境では60秒以内）を延ばさず、窓を跨ぐ再pollの前に
新しいユーザー入力・承認・失敗・通知要否を確認します。無変化だけを理由に
新しい管理コマンドを増やしません。

`functions.exec`のJavaScriptには、この契約上、途中で届いたユーザー停止要求を
直接読むAPIがありません。進行中のbatchやホスト側での中断が、子プロセスの終了まで
保証するともみなしません。停止後のセッション状態を確認できなければ「停止未確認」。
未知のPID探索・一括kill・自動再起動は追加しません。

## ホスト側に残る範囲

単一処理について、モデルに戻らず長時間pollしながら、ユーザー停止・承認・必要な
進捗を即時処理し、最終結果を欠落なく一度だけ届ける機能は、この共通手順では
実装しません。これにはホストの停止伝播・通知・配送契約が必要です。
非公開API、Codex内部改変、別SDKへの移行、Taskgov Runner変更は行いません。
ホスト対応がない間も、上記の短い1回集約だけは両群へ同じ条件で準備できます。

## 計測と確認

次回承認済みRunでは既存の使用量計測に加え、公開操作から次を区別します。

- 実`write_stdin`呼出数（batch内部も各1回）、外側`functions.exec`/`wait`呼出数。
- 待機だけのモデル応答数。編集等を含む応答への混在で分類が変わることも記録。
- 空チャンク、途中出力、終端結果、出力不明・欠損、および必要な進捗通知。
- 開発全体のinput/cached/output/reasoningと応答数。Guardianと実施者費用は別枠。

既存の`TOKEN_USAGE.md`と各Runの凍結集計定義を維持し、元ログを公開成果物やTask DBへ
複製しません。新しいrun資料に適用手順のhashと両群の適用状況を残し、片側不適用や
ツール契約差があれば同条件比較としません。

入力根拠は`runs/run-11/RESULTS.md`と`runs/run-11/response-trace/FINDINGS.md`。
Run11の待機専用応答は33対6、実pollは40対35でした。33応答や対応トークン全額を
削減可能とは扱いません。次回実測前の成果は、適用方式・手順・代表シナリオの確認
までであり、開発全体の効果は未計測です。

代表シナリオは同じ関数を使う`wait_relay_checks.cjs`で、外部操作なしに確認できます。

Nodeはこのオフライン検査だけに使用（確認環境v24.14.1）し、検証先へ導入しません。
mock検査は実際のDesktopの停止伝播や配信保証を証明しない点は上記のとおりです。

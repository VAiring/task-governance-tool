## 1. 要旨

本提案の中心は、次の配置方針である。

- **通常操作では、対象を限定した確認だけを行う。**
- **封印時（証拠・完了が不変になる瞬間）には、必要な関係検証を行う。**
- **全体監査は、バックアップのコピー側と、明示的な診断経路へ集約する。**

v1 で提案した「監査台帳とファイル情報で可変DB全体の合格状態を使い回す」仕組みは、本改善に先立って必須化しない。可変DBでは通常更新でもファイル情報が変わり、使い回しの失効条件が成立しないためである（§7）。監査結果の再利用は、対象・範囲・規則の不変性が別途保証できる場合に限る任意施策として §11 に分離する。

## 2. 背景と問題

現行実装では、整合性チェックが操作経路の各所に組み込まれている。静的実測では以下の規模になっている。

- 各 repository が DB 接続ごとにスキーマ照合や履歴比較を実行する経路がある（所見 S-10、Q-H4）。検証系呼び出しは本体全体で205件、スキーマ版数の照会は静的117回。
- DB全体を走査する系の検査（`integrity_check`／`quick_check`／`foreign_key_check`）が読み取り経路や Viewer のメタデータ検証などにも混在している（S-11、Q-M5）。
- 検証ロジック自体も複製されており、同型の検証実装が複数系統ある（R-01、S-09）。

ただし、これらの静的件数は「当たりを付ける材料」であり、どの施策が性能改善の主部分になるかは動的測定で別途評価する（§12）。既に測定済みの改善（通常応答の Usage 取得、Evidence 公開、Usage 再照合など）と混同しない。

## 3. 前提

1. **ガバナンスと、その証拠収集・記録が本 skill の正式要件であり本質である。** 本提案は検証を減らす提案ではなく、同じ保証を効果のある場所で得るための配置の提案である。
2. **全ての書き込みは本コードのトランザクションを通る。** 仕様上、LLM が DB を直接操作することは想定されていない。
3. **前提2に反する直接操作への保証は設計対象外とする**（§10 非目標）。
4. 現行契約を尊重する。特に、**`doctor` は本質的に read-only で状態を変更しない**（setup-state-specification の Doctor Contract）、**通常バックアップの全検証はコピー側で実施済み**である（同 Backup の契約）という2点は、本提案の前提として組み込む。

## 4. 基本原則

### 原則1：チェックのコストと頻度は反比例させる

コストが O(DBサイズ) または O(オブジェクト数) のチェックは、頻度の低いイベントにしか置かない。頻繁な経路に置いてよいのは、O(1) の確認、または対象オブジェクトに限定されコストがその範囲で閉じる確認だけである。

### 原則2：チェックが意味を持つのは「信頼状態が変わり得た」か「信頼境界を越える」とき

前回の検証以降その対象が不変で、変更経路が検証済みのトランザクションに限られるなら、再チェックの結果は変わらない。逆に以下の場合は、経路の途中でも対象限定の確認に意味がある。

- 対象が変更され得た（移行、復旧、取込、世代の切替）。
- その対象を、不変な決定（証拠の封印、完了の seal、判定への採用）の基礎としてこれから消費する。
- 外部から到着したデータを信頼境界の内側へ取り込む。

### 原則3：検出遅延の扱いは対象で分ける

全体監査を経路から外すと、対象外の過去データの破損検出は次のバックアップ／診断まで遅れ得る。この遅延を一律に「実害は小さい」とは断定しない。バックアップ自体が無効・失敗中の可能性もあるためである。

線引きは対象で分ける。**現在の操作・判断に使うデータについては、対象限定の確認を経路に残し、検出を遅らせない。** バックアップ／明示診断へ移すのは、現在の操作の対象外である過去データの全体監査に限る。

### 原則4：ハッシュが保証するのは「封印された内容の不変性」だけ

ハッシュ一致は、封印された内容が記録時から変わっていないことを保証する。それ以上、つまり「現在の Task／Contract／対象世代に対してその証拠が有効か」「後継のレビューに置換されていないか」「復旧後に参照してよいか」は保証しない。

したがってハッシュ照合で置換するのは**封印内容の不変性確認に限る**。適用可能性（対応関係・世代・置換・復旧後の有効性）の確認は、関係する対象に限定して残す。これは全件検査を残すという意味ではない。

また、ハッシュ照合自体も、大きな対象を繰り返し読み込めば重くなる。コストは「対象サイズ × 照合回数」であり、無条件に「性能懸念が生じない」とは言わない。同一操作内での照合結果の再利用など、読取量と反復回数を設計時に確認する。

## 5. チェックの分類

配置を議論するため、現行で混在しているチェックを分ける。なお `foreign_key_check` は物理破損の検査ではなく参照整合性の検査であり、ここに正しく分類する。また `quick_check` は `integrity_check` の部分集合的な高速版であり、検査内容が異なるため単純な代替関係にはない。どちらを使うかは、必要な検査内容から決める。

| 分類 | 内容 | コスト特性 | 例 |
|---|---|---|---|
| A. 物理整合 | DBファイル／B-tree レベルの破損検出 | O(DBサイズ) | `PRAGMA integrity_check`、`PRAGMA quick_check`（部分集合） |
| B. 参照整合 | 外部キー関係の不整合検出 | O(対象テーブル群) | `PRAGMA foreign_key_check` |
| C. スキーマ契約 | DDL が期待と一致するか、版数が正しいか | O(オブジェクト数)〜 | DDL の正規化比較、版数照会 |
| D. 意味的整合 | 行間の関係・来歴・不変条件がドメイン規則を満たすか | 対象範囲に比例 | 来歴関係の検証、バンドルの整合、重複・欠落の検出 |
| E. 封印内容の照合 | 封印オブジェクトが記録時の内容と同一か | O(対象サイズ × 回数) | ハッシュ照合 |

## 6. 配置基準

| 層 | タイミング | 置くチェック | 置かないもの |
|---|---|---|---|
| L0 | 常時（制約） | 外部キー、UNIQUE、CHECK、トリガ等の DB 制約。接続ごとの `foreign_keys=ON`（安価なため維持） | 追加クエリによる再確認 |
| L1 | 通常操作（読み取り・書き込み） | **対象限定の確認のみ**。その操作が使う・壊し得る対象についての、範囲の閉じた確認（版数の確認、対象行の不変条件、対象オブジェクトの E 照合と適用可能性の対象限定確認） | DB全体・対象外の過去データに対する A／B／C／D |
| L2 | 封印・受入の瞬間 | 対象オブジェクトグラフに対する D（必要な関係検証）の全量、および記録時のハッシュ確定。証拠の記録、レビュー受領、完了の seal、外部データの受入が該当 | 対象外への波及検証 |
| L3 | バックアップ | **全体検査はコピー側へ集約する**（§7.1）。元 DB 側は、コピー取得に必要な局所確認のみ | 元 DB への全体検査の追加 |
| L4 | 移行（マイグレーション） | 移行の前後および最終記録後の、データ保持確認と構造検査。削減基準は §7.2 | 同一状態に対する同一保証の重複 |
| L5 | 明示診断（doctor 等） | A〜D のフルスイープ。ただし **`doctor` は結果を返すだけとし、永続記録はしない**（§7.3） | read-only 契約を破る書込み |
| 昇格 | 具体的な不整合の兆候があるとき | 回復の失敗、または具体的な不整合を示す事象があった場合に限り、全体検査への昇格を検討する。**ホットジャーナルからの正常な回復だけでは昇格させない**（それは SQLite が中断した更新を戻す正常な仕組みであり、回復した事実だけでは追加の全体検査は要らない） | プロセス中断・通常のキャンセル・ロールバック可能な失敗全般、およびホットジャーナルの正常回復を条件にすること |

### スキーマ検証の再利用について

接続ごと・repository ごとのスキーマ全件照合（S-10、Q-H4）は集約の対象とする。ただし再利用には、**別プロセスによる移行・復旧で状態が差し替わる可能性を踏まえた失効条件**が必要であり、「プロセス開始時に版数を1回読む」だけでは不十分である。再利用の単位（同一接続内／同一スナップショット内など、現行契約で既に共有が認められている範囲）を明示し、その範囲を超える再利用は失効条件を設計してから導入する。

### 受入検査の維持

初回構築・復元・正規化、および移行後の公開前については、現行の受入検査を維持する。これらを L2（封印・受入時の関係検証）だけへ縮小しない。受入は信頼境界を越える操作であり、通常操作の対象限定化の対象ではない。

## 7. 個別論点

### 7.1 バックアップ：全体検査はコピー側に集約する

現行実装は既に、現用 DB から整合したコピーを取得し、現用側の接続を閉じてから、コピー側で schema／integrity／foreign-key／関係／privacy の検証を行っている（setup-state-specification の Backup 契約）。通常バックアップの全体検査はこのコピー側に集約し、**元 DB ではコピー取得に必要な局所確認だけを行う**。v1 の「バックアップ前に元 DB を全検査する」は、現行より処理を増やすため撤回する。

なお、コピー側の検査合格が保証するのは内容の健全性であり、復元先との互換性や、復元後の移行までを無条件に保証するものではない。復元時は §6 の受入（L2）として別途確認する。

### 7.2 移行：削減基準は「回数」ではなく「同一状態への同一保証」

現行の保持スナップショット比較には、構造検査とは別に、移行前の列値・行ID・履歴を失っていないことの確認が含まれており、比較は「移行処理後」と「最終的な移行記録の挿入後」という**異なる状態**に対して行われている（database-specification の Preservation Across Review Migrations）。SQLite として正常でも移行コードが行を消すことはあり得るため、最終状態でのデータ保持確認は残す。

重複削減は「中間だから廃止」ではなく、**同じ状態に対する同じ保証の重複を削る**ことで行う。どの状態にどの保証が必要かを先に列挙し、重なるものだけを対象とする。

### 7.3 doctor と監査結果の保存

`doctor` は状態を書き換えないことが契約である。異常な DB を診断するために、その DB への書込み成功を前提にしてはならない。したがって `doctor` は結果を返すだけとする。

全体検査の結果を永続保存したい場合は、明示的に書込みを認めた経路（バックアップ検証の記録など）へ分ける。また、汎用の監査台帳を新設する前に、**既存のバックアップ検証記録を利用できる範囲を整理する**ことを先行作業とする。

### 7.4 監査履歴と省略根拠の分離

以下は混同しない。

- **監査履歴**：ある時点の対象を検査したという事実の記録。それ自体は有用であり、書込みが認められた経路では残してよい。
- **検査の省略根拠**：対象内容・検査範囲・検証規則が変わっていないことの確認。監査履歴が存在すること自体は省略根拠にならない。

v1 では、ファイルの inode／size／mtime とスキーマ版数を省略根拠（失効条件）に据えたが、通常の Task 更新でもこれらは変わり得るうえ、証跡を同じ DB に保存する処理自体もファイル情報を変えるため、この条件は成立しない。撤回する。

## 8. 既存チェックの移行基準

| 判定 | 条件 | 扱い |
|---|---|---|
| 残す（対象限定） | 現在の操作が使う・壊し得る対象への確認 | 範囲を対象に閉じて残す |
| 残す（封印時） | 封印・受入の対象に対する関係検証（L2） | 対象グラフに限定して全量を残す |
| 制約へ移す | DB 制約で等価に担保できる | クエリによる確認を削除し制約に寄せる |
| ハッシュ照合へ移す | 封印内容の不変性確認（分類 E の範囲のみ） | ハッシュ照合に置換。適用可能性の確認は対象限定で別に残す |
| コピー側／明示診断へ移す | 対象外の過去データに対する全体監査（A／B／C／D） | バックアップのコピー側検証、または明示診断へ移す |
| 削除する | 同じ状態に対する同じ保証が他の層で得られており、重複であることが示せる | 削除する |

適用例：

- 接続ごとのスキーマ全件照合 → 再利用単位と失効条件を定めたうえで集約（S-10、Q-H4）。
- 読み取り経路に混在する全体スキャン系検査 → 対象が現在の操作に関係するものは対象限定化し、関係しないものは L3／L5 へ（S-11、Q-M5）。
- 読み取り時に取得済みの行を再 SELECT して関係検証する処理 → 封印時（L2）に完結させ、読み取り側は E 照合＋適用可能性の対象限定確認に置換する（D-M21、Q-M2）。**ただしハッシュ照合への置換は封印済みオブジェクトに限る。** Task の現在状態など変更され得る行には適用できず、可変行の重複取得は、同一の読取状態（同一スナップショット）で取得・検証済みの値を共有することで削減する。すべてをハッシュ方式へ変える必要はない。
- 移行スナップショットの反復 → 状態×保証の対応を列挙し、同一の重複のみ削減（Q-M4 の評価を本基準で読み替える）。
- 存在確認 SELECT → INSERT の2往復 → `ON CONFLICT` 等による1往復化。配置とは別軸だが、同種の「確認のためのクエリ」としてあわせて整理する（Q-H5）。

## 9. 移行手順（段階実施）

1. **棚卸し**：現行チェックを分類 A〜E と配置層で一覧化する。あわせて、既存のバックアップ検証記録が監査用途にどこまで使えるかを整理する（§7.3）。
2. **対象限定化**：通常操作の経路に残す確認を「対象が閉じているか」で仕分けし、対象外の全体監査を経路から分離する。
3. **コピー側・診断への集約確認**：全体監査の受け皿がバックアップのコピー側検証と明示診断に揃っていることを確認し、不足分だけを足す（既存の仕組みの二重実装をしない）。
4. **スキーマ検証の集約**：再利用単位と失効条件を設計し、接続ごと検証を集約する。性能効果はこの段階で動的測定する（§12）。
5. **経路側の除去**：受け皿で等価な保証が得られることを確認しながら、操作経路に残った全体チェックと重複を順に外す。各段階で既存テストによる回帰確認を行う。

## 10. 非目標

- 本コードを経由しない DB 直接操作（LLM の勝手な操作を含む）への保証。仕様上の想定外とする。
- DB ファイルへの書き込み権限を持つ主体による意図的な改竄の検出。
- チェック頻度の単純な削減。本提案は「対象と場所の置き直し」であり、L2（封印時）と L3（バックアップのコピー側）の検証は必須として維持する。

## 11. 任意施策（今回必須化しない）

- **監査結果の再利用**：ここで任意施策とするのは「追加の汎用機構」である。既存の、不変バックアップ等に対するハッシュ・検査範囲・検証規則に基づく再利用は、現行の仕組みとして維持する。そのうえで、対象内容・検査範囲・検証規則の不変性がファイル情報に依らない方法で確認できる場合に限り、全体検査の結果を再利用する汎用機構を将来の選択肢として残す。本改善の前提にはしない。
- **汎用監査台帳の新設**：既存のバックアップ検証記録で不足することが判明した場合に検討する。

## 12. 評価方法

- 本提案の各施策の性能効果は、静的な呼出し箇所数ではなく、対象経路の動的測定（クエリ発行数、応答時間）で評価する。プロジェクトには SQL トレース基盤（所見 Q-L1）が既にあるため、それを用いる。
- 既に測定済みの改善領域（Usage 取得、Evidence 公開、Usage 再照合など）と、新規施策の効果は分けて報告する。

回帰テストの受入条件には、性能と正しさの両方を固定するため、以下を加える。

- 無関係な Task が増えても、通常操作の検査量（クエリ発行数）が増えないこと。
- 対象自身の不整合は、対象限定の確認で検出できること。
- 復元・世代変更の後に、古い検証結果を使い回さないこと。

## 13. v1 からの改訂点（設計レビュー指摘への対応）

| # | 指摘 | v2 での対応 |
|---|---|---|
| 1 | ファイル情報（inode／size／mtime）を監査結果の有効条件にすると通常更新でも失効し、証跡保存自体もファイル情報を変える | 当該条件を撤回。監査履歴と省略根拠を分離し（§7.4）、再利用は任意施策へ（§11） |
| 2 | ハッシュ一致は現在の完了判断への適用可能性まで保証しない | ハッシュの範囲を封印内容の不変性確認に限定し（原則4）、適用可能性の確認は対象限定で残す（§8） |
| 3 | バックアップの二重全検査は現行より増える。現行はコピー側検証＋結果再利用が既にある | 元 DB の全検査案を撤回し、コピー側へ集約する現行方針を明記（§7.1）。互換性・復元後移行は保証範囲外と明示 |

## 14. 決定事項（承認いただきたい点）

1. 配置方針（§1：通常操作は対象限定／封印時は関係検証／全体監査はコピー側と明示診断へ集約）を、整合性チェックの正規ルールとして採用すること。
2. バックアップの全体検査はコピー側に集約し、元 DB には全体検査を追加しないこと（§7.1）。
3. `doctor` は結果を返すだけとし、監査結果の永続保存は書込みを認めた経路に分けること（§7.3）。
4. ハッシュ照合の適用範囲を封印内容の不変性確認に限定し、適用可能性の確認を対象限定で残すこと（原則4、§8）。
5. 監査結果の再利用と汎用監査台帳は今回必須化せず、任意施策として分離すること（§11）。
6. 直接操作への保証を非目標として明記すること（§10）。

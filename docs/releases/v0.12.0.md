# task-governance-tool v0.12.0

`task-governance-tool` 0.12.0 is the current unpublished local candidate. It
has not been pushed, tagged, published, or attached to a GitHub Release, and
this note grants no authority for any such external operation. The immutable
published v0.10.0 artifact and the immutable v0.11.0 candidate-lineage note
remain unchanged.

## Candidate Changes

- Schema v18 activates capture-versioned authority snapshots, whole-field
  Contract criteria, evidence references, and Git artifact manifests as the
  local Evidence Ledger capture foundation.
- New Verification Receipts use a Taskgov-owned subject bound to the locked
  capture-version-1 authority snapshot and verification criterion.
  `verification receipt add` no longer accepts `--command-label`, and no caller
  subject option replaces it. Migrated pre-v18 Receipts retain a version-0
  legacy-label projection without being upgraded.
- Independent and self-review Receipt writes require declared reviewer class,
  model state, Skill state, and context relation. Declared identifiers are
  conditional, and review profile, lens, and method flags are repeatable
  bounded sets. Public Review Receipts distinguish native v1 provenance,
  migrated v0 absence, and `not_required` null without upgrading the parent
  Receipt assurance.
- Migrated capture-version-0 targets are read-only lineage. A fresh target is
  required before recording a new Verification Receipt, Review Receipt, Review
  Finding, or completion source; the old target is never upgraded in place.
- Durable/read and internal-derived verification capacity is 1,000 characters.
  Explicit public `task add` and `task edit --verification` admission is also
  1,000 characters in this candidate. Source-schema-aware migration and recovery
  reject invalid state before DDL, publication, or business mutation.
- Viewer snapshot v4 accepts source schemas v5-v21. It validates schema-v18+
  subject, provenance, capture, and Bundle bindings plus the source-appropriate
  Bundle-v2 and Runner tagged graph, but exposes no new field, panel, filter, or
  control.
- Schema v19 seals one immutable Bundle v1 for each native completion and
  maintains canonical Evidence JSON v1 at fixed `state/current/evidence/index.json`
  and `state/current/evidence/bundles/<completion-evidence-bundle-id>.json`
  paths. Schema v20 preserves existing Bundle-v1 bytes and digests, seals
  Bundle v2 with a derived verification basis and null Runner observation for
  each new native completion, and publishes Evidence index v2 with
  `bundle_format_version`. Pre-v19 cycles remain `legacy_unknown`; setup
  repairs the projection, doctor reports its stored status, and post-commit
  order is Evidence, Viewer, then backup.
- Schema v21 widens only the frozen Runner gate-basis discriminators and
  preserves schema-v20 Runner rows as gate-ineligible audit history. Accepted
  TG-M24.3B kept new completions on the existing M21 caller-attestation or
  not-required branches; accepted TG-M24.3C additionally admits an exact-current
  complete-plan Runner pass as a Receiptless Runner-observation basis, while the
  exact closed no-launch fallback alone returns to the M21 Receipt branch.
  Accepted TG-M24.4A validated supported, fallback, failure, cleanup, and
  privacy flows. Current TG-M24.4B is acceptance-only and changes no candidate
  behavior.

The existing trusted-local target-set route remains the sole Runner trigger.
The candidate adds no Runner command, Analyzer or network/model invocation,
Viewer Evidence surface, or new public leaf. It adds only the closed
`verification_route` and nullable `blocking_code` to target-set JSON success.
With no post-target `task show`, the manual/fallback no-finding Tier 2 flow is
bounded to ten governance calls, or eleven when the existing Effort Advisory
boolean enables its single read; the Receiptless Runner-pass path is one call
lower.

## Public Receipt Examples

Only when target set returns `verification_route=receipt_required`, run
verification outside Taskgov and record its Receipt:

```powershell
python .agents/skills/task-governance-tool/scripts/taskgov.py verification receipt add <task-id> --result pass --duration-ms <milliseconds> --scope-coverage full --expected-target-generation <generation> --json
python .agents/skills/task-governance-tool/scripts/taskgov.py review receipt add <task-id> --reviewer <reviewer-key> --kind independent --verdict pass --summary "No blocking findings" --reviewer-class llm --model-state declared --declared-model-id <model-id> --skill-state not_used --context-relation fresh_context --review-profile general --review-lens correctness --review-method review_packet_inspection --json
```

Taskgov never executes the verification command or launches a reviewer. Review
provenance is a bounded caller attestation; it does not authenticate identity
or prove actual model/Skill execution, competence, independence, diversity,
quality, or truth.

## Privacy And Local-Only Boundary

Verification Receipt retention remains deny-by-default. Native Receipts store
only the tool-owned subject, closed result, duration, full/partial coverage,
Task and Contract ownership, exact target basis, and recording time. They never
store or execute a verification command body or arguments and never retain exit
code, stdout/stderr, stack trace, environment, logs, exceptions, prompts,
diffs, credentials, arbitrary coverage prose, or debug variants.

Review provenance retains only the closed scalar/code declarations, bounded
declared identifiers, target binding, assurance/producer values, and digest.
It adds no identity authentication or assurance upgrade.

The Skill remains project-scoped, local-first, and standard-library-only. It
does not mutate target-project files or Git state, use a network service,
create an external Issue or PR, launch a browser, or grant publication
authority.
